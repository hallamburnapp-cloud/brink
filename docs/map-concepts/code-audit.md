# What this repository gives a map game

## Reuse as is

- **Seeded RNG (xoshiro128**)** (`/home/user/brink/src/engine/rng.ts`): This can be used as it is. Its state is four 32-bit integers that can be saved and restored, and a seed string always produces the same sequence. It has weightedIndex, shuffle and fork(label). fork gives each subsystem its own stream (spread, counter-force, events, headlines, bots), so adding a subsystem later does not change the results of the others. It uses only integer maths (Math.imul and shifts), so it gives the same numbers on V8, JavaScriptCore and SpiderMonkey; if two devices disagree, the RNG will not be the cause. Measured in Node: about 118 million draws per second. A toy model of 200 regions over 18,000 ticks (30 minutes at 10 Hz) took about 115 ms per game, so the RNG will not slow a real-time simulation or a headless balance run.
- **Safe local persistence** (`/home/user/brink/src/meta/storage.ts`): This has no game-specific code. Every read and write is wrapped in try/catch and falls back to memory when storage is unavailable, and there is a test hook. It works for settings, autosave envelopes and local records. Large mid-game saves should go to native storage on mobile and Steam Cloud on desktop (see risks).
- **Web unlock token client** (`/home/user/brink/src/meta/unlock.ts`): Has no game logic. It verifies ECDSA P-256 tokens offline with WebCrypto, handles the /unlocked?session_id= page Stripe redirects back to, restores a purchase by email, and keeps verified results in memory. The plan string 'endless' is just a label; renaming it means changing it here and in worker/src/index.ts and worker/src/crypto.ts together. Web build only.
- **Stripe unlock Cloudflare Worker** (`/home/user/brink/worker/`): This is a separate package with its own tests (crypto, routes, webhook). It takes a Stripe Payment Link purchase, checks the Checkout Session, and returns a signed token; it also handles the webhook, restore-by-email with a rate limit, CORS and an optional price check. None of it depends on the game. The only work is configuration: the KV namespace ids and STRIPE_PRICE_ID in wrangler.toml are still REPLACE placeholders, and ALLOWED_ORIGIN needs the real URL. It must not ship in the iOS or Android builds.
- **Web Audio engine core** (`/home/user/brink/src/audio/engine.ts, /home/user/brink/src/audio/voice.ts, /home/user/brink/src/audio/drone.ts, /home/user/brink/src/audio/heartbeat.ts, /home/user/brink/src/audio/storage.ts, /home/user/brink/src/ui/sound.ts`): All of this is general-purpose. The AudioContext is created only on the first tap or key press (needed on iOS), and there is a sound chain with a compressor, master volume and a saved mute setting. There is a long-running drone whose intensity changes smoothly and a scheduled heartbeat or pulse. A real-time map game can tie the drone to how close the counter-force is to winning and the pulse to the final minutes. No audio files and no network. Only the list of individual sound effects in sfx.ts needs new entries (listed under changes).
- **Content hot-reload plumbing** (`/home/user/brink/tools/vite-plugin-content.ts, /home/user/brink/src/content/index.ts`): Exposes compiled content as a virtual module and hot-reloads it during development, keeping the last good version if a YAML file is half-edited. It prints validation issues to the terminal and the in-game dev banner, refuses invalid content in production builds, and can be relaxed with BRINK_CONTENT_LENIENT. It does not care what the YAML contains, because it calls loadContent(); only load.ts and schema.ts change.
- **Packaging: itch.io zip** (`/home/user/brink/tools/zip.ts, /home/user/brink/tools/build-itch.ts`): The zip writer is tested, and the itch build is the 'everything unlocked' web version with a relative base path. Only the viewport note in the README changes, from 430×860 portrait to a landscape size.

## Build new

- **Fictional world map asset and build pipeline** (Tooling 1 week. Art direction and the map art itself 2–3 weeks, probably commissioned. This piece decides whether the main screen works as one beautiful picture.): Use an invented world (new continents and about 40–60 regions), not real-looking geography. A real-looking map forces naming or leaving out real states and brings border disputes into some app-store markets; an invented one also helps keep it from looking like a Plague Inc clone. Draw the map as one SVG in Inkscape or Figma with an id on every region path, plus terrain and biome layers. A new tools/map-build.ts uses @resvg/resvg-js (already a devDependency for the OG image) to produce: (1) a region-ID mask drawn with crisp, non-blended edges, with the region index encoded in the colour channels; (2) a terrain colour texture, 2048×1024 webp for phones and 4096 for desktop; (3) a coastline and border distance field for glows. It also computes adjacency from shared border pixels, centre points, label anchors, areas and route endpoints, and writes map.json for the validator to check against regions YAML.
- **Map renderer (WebGL2, with a Canvas 2D fallback)** (A basic version in 1 week. Beautiful and 60 fps on a mid-range phone: 3–4 weeks including testing on real devices.): A full-screen quad with a fragment shader. Each pixel looks up its region in the ID mask, then reads that region's live state from a small state texture (one texel per region: spread, control, counter-force presence, highlight) that is updated each tick. Spread grows as organic blotches rather than flat fills: a fixed noise texture is thresholded against the region's spread value, with a light dither over time. Border and coast glow come from the distance field. Instanced quads draw route arcs, moving units and pulses. Labels and tappable markers are DOM elements placed through the camera transform and updated at a throttled rate. Draw only while the state or camera is changing or an animation is running. Cap the pixel ratio at 2 (1.5 on low-end devices), restore after WebGL context loss, and keep a Canvas 2D fallback with flat region fills. Use raw WebGL2 (about 15–25 KB of our own code) or ogl (about 25 KB gzipped). Not PixiJS v8, whose roughly 150 KB gzipped would use up most of the 250 KB budget.
- **Camera and input (touch pan/zoom, mouse, keyboard, gamepad)** (1–1.5 weeks): Pointer Events with touch-action:none on the map, plus a gesturestart preventDefault so iOS Safari does not zoom the whole page (it ignores maximum-scale=1 in index.html). One-finger pan with inertia, pinch zoom around the midpoint between the fingers, mouse wheel and trackpad pinch (wheel with ctrlKey), double-tap to zoom, soft clamping at the edges, and a threshold that separates a tap from a drag. Region picking reads a CPU copy of the ID mask, so a tap is a single lookup. Keyboard: arrows or WASD to pan, +/- to zoom, space to pause, 1/2/3 for speeds. Gamepad API support for Steam Deck. About 600 lines.
- **Tick-based deterministic simulation core** (2–3 weeks to the first playable version, then ongoing tuning): A new pure module with no DOM access that replaces src/engine/run.ts and serves the game, the balance simulator and the tests. Fixed timestep: for example, one tick is a quarter of a game day; 1x is 2 ticks per second, then 2x, 4x and an unthrottled maximum for bots. An accumulator loop clamps large frame gaps, and the game pauses on visibilitychange and pagehide. Per-region state lives in typed arrays (population, affected, controlled, counter-force presence), with a small JSON envelope for currency, owned upgrades, counter-force progress, RNG state, tick and pending events. Spread inside a region follows a growth curve; spread between regions travels over borders and routes, with occasional jumps. Use fixed-point integers or lookup tables, never Math.exp or Math.pow inside the simulation (see risks). The points currency comes from milestones and tappable pickups; the pickup must look nothing like Plague Inc's bubbles. The counter-force has its own rising rate and reacts to how visible you are. Win and loss checks. Every player action is logged as (tick, action) so a game can be replayed. Autosave every N seconds and on pagehide. Estimated cost is under 1 ms per tick at 200 regions, so it can run on the main thread; move it to a Web Worker only if profiling shows a need.
- **Upgrade tree (data and UI)** (1.5–2 weeks for code, plus about 1 week to write and tune 40–60 upgrades): Upgrades live in YAML (id, tree, tier, cost, prerequisites, refund, effects written as modifiers, icon, a blurb of one sentence or less) and resolve through the reused modifier resolver. Three tabs, each a hex or node grid with SVG lines for prerequisites, and clear locked, affordable and owned states. Each node gives a one-line preview of its effect in words, not a table of numbers (the owner's first complaint). Long-press or hover opens the detail. Buying an upgrade pulses the regions on the map that it affects, so the choice visibly matters (the owner's second complaint).

## Technical risks

- Overall estimate: about 14–20 developer-weeks to a polished release on all three channels, not counting commissioned map art and music. A web-only vertical slice (one map, one upgrade tree, the ticker, a win and a loss) takes about 5–7 weeks.
- 60 fps is not guaranteed on mid-range phones. A full-screen shader map at pixel ratio 3 is limited by how fast the GPU can fill pixels, and phones slow down when they heat up and drain battery over a 30-minute real-time session (Plague Inc is a native app). Mitigation: cap the pixel ratio, draw only when something changes, offer quality tiers, and test on real devices from week 2.
- Tauri renders with a different browser engine on each system: WebView2 (Chromium) on Windows, WKWebView on macOS and WebKitGTK on Linux. A native Steam Deck build therefore runs on WebKitGTK, whose WebGL is the slowest and buggiest of the three. Either prototype on a Deck early or consider Electron (the same Chromium everywhere, at the cost of a roughly 150 MB download).
- Determinism can break between browser engines. Math.exp, pow, log and sin are not guaranteed to round the same way in V8, JavaScriptCore and SpiderMonkey, so one 'Daily World' seed or one replay could play out differently on Safari and Chrome. The existing RNG is integer-only and safe, but a growth model written with Math.exp would not be. Use fixed-point integers or lookup tables in the simulation and compare state hashes across engines in Playwright.
- Real time is not the same as frame time. requestAnimationFrame stops in background tabs, iOS suspends WebViews, and a simulation driven by frame gaps will jump forward or give different results. The simulation must use a fixed step with clamped catch-up and save on pagehide. Separately, Safari can clear localStorage for websites that have not been used for 7 days (home-screen PWAs are exempt), which would lose 30-minute saves. Use native storage in Capacitor and Steam Cloud on desktop.
- A continuous, chaotic simulation is much harder to balance than two-choice cards: small parameter changes swing the results. Bots cannot judge feel, such as how soon the map visibly changes or the shape of the tension. The existing targets and policies do not carry over. BLOCKERS B-004 already shows a target failing because of how the bot played, not because of the game. Plan time for human playtests.
- Risk of looking like a Plague Inc clone. A map with spreading colour, tappable point pickups, a news ticker along the top and a cure-style progress bar along the bottom is Plague Inc's screen. Store reviewers can reject copycats (App Store guideline 4.1) and players will say so in reviews. Make the theme, layout, wording and the way points are collected clearly different.
- Texture limits. Older and low-end phone GPUs cap textures at 4096 pixels and have little memory. Workbox's default 2 MiB limit per file would leave large textures out of the offline cache without any warning. Large images also slow the first load of the web link. Use a 2048 texture tier for phones, atlases, and a texture budget enforced in the size check.
- A normally rendered region-ID mask blends colours along the edges, creating region ids that do not exist. That gives wrong taps and visual artefacts in the shader. The mask must be rendered with crisp edges (resvg's shape-rendering crispEdges) or by our own polygon rasteriser.
- Phones can drop the WebGL context when the app is backgrounded or memory is short. It must be restored, or the map comes back black.
- Browser gestures can fight the map. iOS ignores maximum-scale=1 in /home/user/brink/index.html, so a pinch can zoom the page instead. Pull-to-refresh and edge back-swipes can clash with panning on Android and iOS. Needs touch-action:none, a gesturestart handler and overscroll-behavior.
- Payment is split three ways. Stripe tokens work on the web only. iOS and Android require store billing for digital unlocks; regional exceptions exist but keep changing. Steam requires a Steam purchase. That is three separate purchase checks to build and test. The Worker's restore-by-email gives a token to anyone who types a buyer's email address (limited to 10 a day per email); acceptable for a small unlock, but worth stating. The plan string 'endless' is hard-coded in /home/user/brink/worker/src/index.ts, /home/user/brink/worker/src/crypto.ts and /home/user/brink/src/meta/unlock.ts, and they must change together.
- The native shells have never been built. There are no ios/ or android/ projects, no Capacitor packages and no @tauri-apps/cli; the icons are not generated, and Steamworks exists only as a stub. Signing, macOS notarisation and store review are all still unknown, and iOS needs a Mac.
- Playwright cannot see what is drawn on a canvas, so DOM assertions say nothing about the map. It needs a test-only hook and screenshot baselines. Headless Chromium renders WebGL in software (SwiftShader), which is slow and gives different pixels from a real GPU. A 15–40 minute game needs a maximum-speed mode for CI to finish in time.
- Preact can be overloaded. Pushing simulation state into signals every frame would re-render the HUD 60 times a second. Keep game state outside signals and send throttled snapshots.
- Most of the existing code is built around cards and should be retired, not adapted: /home/user/brink/src/engine/run.ts (1,458 lines), leverage.ts, night.ts, fixture.ts and types.ts; src/ui/store.ts (792 lines); src/sim/simulate.ts (1,961 lines); src/sim/policies.ts (858 lines); every card screen and component; the portrait art manifest; and the content/ and content-crisis/ packs. ENGINE.md, HOTEL.md and REDESIGN.md become obsolete. Adapting this code in place would pull acts, seats, pieces and leverage back in and produce a fourth card game in disguise.
- Region names could accidentally match real places, brands or offensive words. The FORBIDDEN_WORDS list in /home/user/brink/src/content/validate.ts has only about 60 terms, so it needs a full gazetteer check. A real-looking geography would also bring border-dispute sensitivities with some app stores.
- Text overload could creep back through upgrade tooltips and headlines; the owner complained about too many numbers and walls of text. Enforce length limits and 'words, not numbers' in the validator, as the hotel's voice checks did.
- Accessibility. If spread is shown by colour alone, colour-blind players cannot read the map; use brightness ramps or patterns. A canvas is invisible to screen readers, so the ticker and HUD must carry the essential state as text.
- There is no music, only synthesised sound. A 30-minute real-time session needs a sound bed, which brings licensing or commissioning costs.
- Theme affects store review. Pandemic or contagion themes get extra scrutiny from app stores, and war or nuclear themes raise the age rating. The setting chosen changes both the review risk and how the map looks.
